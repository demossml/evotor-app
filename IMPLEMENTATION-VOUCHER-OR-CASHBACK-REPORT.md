## 2. Что сделано по блокам

### B — DTO, парсер, хранение
- `ResolveVoucher.imageUrl` добавлен, парсится, в логике не участвует (требование B1).
- Парсер толерантен: `id <= 0`, неизвестный `kind`, `value <= 0` — запись отбрасывается;
  отсутствие `vouchers` → пустой список.
- `fixed` трактуется как **копейки** (контракт backend: `30000` = 300 ₽). В 5.2.1 значение
  ошибочно считалось рублями — исправлено, тесты переведены на копейки.

### C — Математика (`data/DiscountCalc.kt`)
- `compute(...)` получил `voucher` и `voucherAllowed` (оба с дефолтами — старые вызовы не меняются).
- `Result` теперь `(free, voucher, cashback, total)`.
- Ваучер: `percent` — от остатка после подарка вниз до копеек; `fixed` — из копеек, не больше остатка.
- **Инвариант:** при применённом ваучере `cashback = 0` (кэшбэк остаётся на балансе гостя).
- `VoucherCalc` больше не дублирует арифметику — делегирует в `DiscountCalc.voucherDiscount`.

### D — Состояние (`data/Choice.kt`, `data/CheckoutChoice.kt`)
- `Choice.normalize(...)` — единственное место, где решается взаимоисключение:
  ваучер обнуляет кэшбэк, кэшбэк обнуляет ваучер, `id <= 0` = «нет ваучера».
- `CheckoutChoice.save(..., voucherId: Int?)` пишет только нормализованное состояние;
  `voucherId()` возвращает `Int?`.
- Тесты: `CheckoutChoiceTest` (5 шт., без Robolectric — нормализация чистая).

### E — UI листа «Лояльность»
- Вместо двух независимых блоков («Кэшбэк» и «ВАУЧЕР») — одна секция **«Скидка»**:
  «Без скидки» / «Списать кэшбэк до N ₽» / «Применить ваучер». Секция появляется,
  только если есть хоть одна доступная скидка; строки про ваучер нет, если ваучеров нет.
- Несколько ваучеров → после «Применить ваучер» список с названием и размером
  (`−15%`, `−300 ₽`); несуммируемый с подарком пункт заблокирован с текстом
  «не суммируется с подарком».
- Включение подарка снимает ранее выбранный несовместимый ваучер и сбрасывает выбор на «Без скидки».
- Ручной числовой код → подсказка «Скидка по ваучеру — только по QR гостя».
- «В чек» передаёт `voucherId` только при выборе ваучера; кэшбэк и ваучер одновременно не уходят.

### F — Чек и `extras.sc`
- `SellLauncher` считает скидку тем же `compute(...)` с ваучером; в `SetExtra` уходит
  `voucherId` только если ваучер реально даёт скидку; лог `receipt_discount`.
- `DiscountIntegrationService`: единый расчёт (было — отдельный `VoucherCalc.discount` поверх
  `calc.total`), лог `extras_written … voucher=<id> voucherRub=<…>`.
- `CardSession.sc`: `voucherId` пишется только при **живом резерве и токене** (`kindOf(c) == "token"`).
  По числовому коду ключа нет никогда.
- Тесты `CardSessionExtrasTest`: 6 новых (QR+резерв → ключ есть; без резерва, по коду, без выбора —
  ключа нет; ваучер+кэшбэк не вместе; плоский и вложенный `sc` идентичны).

## 2а. A2 — ревью кода и риски (найдены при чтении, не все устранены)

| Риск | Состояние сейчас |
|---|---|
| Предпросмотр ≠ реальная скидка | `SellLauncher` считает от `Cart.gross()` (каталог), сервис — от `receiptUnitPrices()` (позиции открытого чека). Формула теперь одна, но база может расходиться, если кассир правил чек в POS. Сознательно не унифицирую: сервис обязан считать по факту чека |
| `CheckoutChoice.clear()` в `finally` сервиса | Ложный вызов убран ранее (D2 прошлой задачи); очистка только на подтверждении/отмене/ошибке — `MainActivity:4597,4609`, `SellLauncher:158,164,172` |
| Потеря выбора при повторном открытии листа | Остаётся: состояние секции «Скидка» живёт в листе и стартует с «Без скидки». Практического вреда нет — лист открывается непосредственно перед «В чек», а после неудачной отправки кассир выбирает заново осознанно |
| Гонка TTL `CardSession` / резерва | Резерв живёт ~30–40 с (backend), сессия карты — 10 мин. Если кассир думает дольше, `reserved = false` и скидка (подарок и ваучер) снимается — это защита от рассинхрона, но касса не подсвечивает причину в листе, только в баннере |
| Ваучер со скидкой больше остатка | `fixed` клампится остатком, `total` не превышает чек — покрыто тестом |

## 3. Расхождения в промпте и принятые решения

1. **`total` — это сумма скидки, а не сумма к оплате.** Пример в §5/C2 («gross 400, voucher 60 →
   total 340») противоречит формуле того же пункта (`total = min(free + voucher + cashback, gross)`)
   и существующим тестам (`freeIsCheapestEligibleUnit`: gross 430, подарок 180 → total 180).
   `ReceiptDiscountEventResult` принимает именно сумму скидки. Оставлена семантика кода и формулы;
   тесты проверяют `voucher = 60`, `total = 60`. **Требует подтверждения владельца**, если
   имелось в виду иное.
2. **Предвыбор единственного ваучерa не делается.** Промпт разрешает («допустим предвыбор»),
   но не требует. Касса не применяет деньги гостя без действия кассира — по умолчанию «Без скидки».
3. **Добавлена ячейка «Без скидки».** При двух вариантах нужен способ отказаться от скидки;
   без неё выбор был бы принудительным.
4. **Guard на backend (`cb` + `voucherId`) не реализован** — по промпту это отдельная задача.
   Касса уже не отправляет оба поля.
