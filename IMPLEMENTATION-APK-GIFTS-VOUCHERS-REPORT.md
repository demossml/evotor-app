## 2. По блокам

### Блок A — база и ревью

Найденные риски (A2):

1. **[критично] `CheckoutChoice.clear()` внутри сервиса скидки** (`finally`) — Эвотор пересчитывает
   чек несколько раз; на втором расчёте выбор льгот уже пуст, и подарок исчезал. Исправлено в D2.
2. `freeEligible` фиксировался в строке корзины на момент добавления — после правки каталога флаг
   устаревал (исправлено в B1: `Cart.applyEligibility`).
3. Позиции-добавки (`optionId != null`) теоретически могли попасть в подарок (исправлено в B1:
   единый фильтр `Cart.giftEligibleLines()`).
4. Пустой список подходящих позиций давал молчаливый `free=0` без следов в логах (B3).
5. Двойной расчёт extras (`SellLauncher` и `DiscountIntegrationService`) — оба на одном
   `DiscountCalc`, но в разные моменты; остаётся архитектурным долгом (см. §6).

### Блок B — freeEligible и расчёт

- Приоритет источников: `freeEligible` с сервера → `countsAsCup` (если сервер не прислал
  `freeEligible` и это не еда) → эвристика `FreeCupRules`. Реализовано в `CatalogApi.mergeWithStats`.
- Единый фильтр подарка `Cart.giftEligibleLines()`: `freeEligible && optionId == null`,
  используется в предпросмотре, в `SellLauncher` и в сервисе — цифры совпадают.
- Логи в момент расчёта:
  - применено: `loyalty_discount reserved=… freeChosen=… freeAvail=… eligibleCount=… freeRub=… cbRub=… op=yes|no`
  - не применено: `loyalty_discount_skip reason=no_card|no_reservation|no_eligible|no_free_available|not_chosen|no_benefit`

### Блок C — UX кассира

Одна короткая фраза (`loyaltyHint`) в панели карты и баннером в листе «Лояльность»:

| Состояние | Текст |
|---|---|
| подарок есть, резерв есть, позиция подходит | «Подарок доступен — примените в листе «Лояльность».» |
| подарок есть, позиции нет | «Нет подходящего напитка в чеке для подарка.» |
| ручной код (нет резерва) | «Для списания подарка нужен QR клиента: по номеру карты подарок не списывается.» |
| занято другой кассой | «Подарок уже зарезервирован на другой кассе. Завершите там чек или подождите.» |
| офлайн | «Нет связи: подарок и кэшбэк недоступны, чашки начислятся после чека.» |
| кэшбэк без резерва | «Кэшбэк спишется только по QR клиента.» |

Карта не найдена/заблокирована — прежние тексты `LoyaltyApi.resolveErrorText` («Карта не найдена…»,
«Карта заблокирована.»). Raw-коды кассиру не показываются.

**C2:** выбор подарка остаётся явным переключателем «Применить подарок / Без подарка», но
**по умолчанию включён**, когда подарок доступен. Это текущее продуктовое решение; если нужно
требовать явного нажатия — меняется одна строка (`var useGift = giftPossible` → `false`).

### Блок D — контракт `sc`

Правила закреплены тестами (`CardSessionExtrasTest`, `GiftRulesTest`, `VoucherTest`):

| Сценарий | `op` | `free` | `cb` | `voucherId` | `ord/qn` |
|---|---|---|---|---|---|
| QR + подарок | есть | 1 | 0 | если выбран | если номер получен |
| QR без подарка | есть | 0 | 0 | если выбран | если номер получен |
| ручной код | нет | 0 | 0 | нет | если номер получен |

`CheckoutChoice.clear` больше не вызывается в сервисе скидки; чистится при подтверждении оплаты,
отмене и на путях ошибок `SellLauncher`.

### Блок E — ваучеры

- `ResolveVoucher` + `VoucherJson.parse` — толерантный (нет поля → пусто, мусор пропускается),
  `toJson/parse` для сохранения в сессии карты.
- Правило скидки зафиксировано: **percent считается от остатка после подарка**, `fixed`
  ограничивается остатком; суммарно не больше чека (`VoucherCalc`).
- Выбор: 0 — блока нет; 1 — предвыбран (снимается); несколько — список с «Без ваучера»;
  несовместимый с подарком (`stackableWithFreeCup = false`) блокируется с пояснением в подписи.
- `sc.voucherId` пишется только при живом резерве; одинаковая логика в `SellLauncher` и сервисе.
- Log: `extras_written … voucher=<id|0>`.

## 5. Зависимость от backend

Работает уже сейчас: подарки (без изменений контракта), `sc` с `ord/qn`.

Ждёт backend:
- `vouchers[]` в `POST /api/devices/loyalty/resolve` (иначе блок ваучеров не появляется);
- приём `sc.voucherId` в `SellHandler` (погашение ваучера и `vouchers.used_at`).

До этого касса полностью работоспособна: парсер толерантен, UI ваучеров просто не показывается.

## 6. Остаточные риски

1. **Два независимых расчёта** скидки (`SellLauncher` при открытии чека и сервис при событии):
   при изменении корзины между этими моментами extras и скидка могут разойтись. Нужен единый
   снимок расчёта — отдельная задача.
2. **F1 не пройден** — реальное поведение PrintExtra/скидок на прошивке не подтверждено.
3. `free` по умолчанию включён при доступном подарке (продуктовое решение, задокументировано).
4. Эвристика `FreeCupRules` остаётся fallback: при отсутствии каталога (офлайн-старт) возможны
   ложные срабатывания; backend всё равно перепроверяет.
5. Ваучеры: формула «процент от остатка после подарка» — наше решение; если backend считает иначе,
   суммы разойдутся (нужно согласовать).
