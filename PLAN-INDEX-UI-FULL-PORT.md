> Документ-основание перед кодом. Составлен по фактам изучения архива `index (1).zip`
> и текущего состояния проекта `ru.sixthcup.evotor` (versionCode 93 / 4.7.7-breaks-close).

## 0. Резюме

| Что | Ответ |
|---|---|
| Дизайн и вёрстка | Переносится на **~100%** (View-система, без Compose) |
| Клиентская бизнес-логика (цены, скидки, комбо, чашки, бонусы, сдача) | Переносится **1:1**, это чистые функции |
| Механики, требующие сервер | **Реализовать заново** (табель, пожелания, перерывы, команда, статистика, резерв бонусов) |
| Механики, требующие фискального слоя Эвотора | **Реализовать через Integration Library** (оплата, внесение/изъятие/инкассация, X-отчёт, закрытие смены) |
| «Скопировать и всё заработает» | **Нет.** ~30–35% прототипа — демо-заглушки без источника данных |

Оценка: **~19–22 рабочих дня клиента** + **~10–15 дней бэкенда** (параллельно).
Даёт: рабочий APK с полным UI `index`, реальными деньгами, фискальными операциями и лояльностью.

### Ключевой факт

Прототип **не имеет источника данных**:

- `grep fetch|XMLHttpRequest|localStorage|sessionStorage|indexedDB` по `app.js` → **0 совпадений**;
- меню — массив `MENU` (12 позиций) прямо в коде;
- гость — `guestTemplate` (Анна К., 6/8 чашек, 428 ₽);
- кассир — `shiftState.employee = "Иванов Пётр"`, касса 15 440 ₽;
- табель — `TS_STAFF` + генератор `buildTimesheetMonth()` на псевдослучайных числах;
- оплата — `setTimeout(…, 1700)` → «Оплачено»;
- QR карты гостя — `qrMarkup()` рисует декоративный QR из `seed = 67`;
- смена, внесение/изъятие/инкассация, X-отчёт — меняют `shiftState.drawer` в памяти;
- пожелания/перерывы — `setTimeout` 800 мс и тост «отправлено».

Отсюда: всё, что в прототипе «просто работает», в продакшене нужно либо считать на клиенте (можно), либо брать с бэкенда (его нет), либо проводить через Эвотор (нельзя подделать).

## 6. Решение, которое нужно принять до кода: модель модификаторов

Это главный риск проекта. В `index` модификаторы — **дельты цены на клиенте**:

```js
unitPrice(item, cfg) = item.price + size.delta + milk.delta + syrup.delta + extras.sum
```

У нас в APK модификатор — **отдельный товар Эвотор** (`Topping.evotorUuid`), который
добавляется отдельной строкой чека. Это фискально корректно: списывается склад, в чеке
видно «Сироп ваниль +30 ₽».

Перенести `index` дословно нельзя: если просто прибавить дельты к цене напитка,
в чек уйдёт завышенная цена напитка, склад молока/сиропов не спишется, а отчёт по
номенклатуре развалится.

### ✅ РЕШЕНО: Вариант A

**Модификаторы остаются товарами Эвотор, но UI приводится к виду `index`:**

| Группа | Как реализуется | Откуда цена |
|---|---|---|
| Размер (250/350/450 мл) | отдельный товар Эвотор на каждый размер («Капучино 450 мл») | Inventory (`PRICE_OUT`) |
| Молоко (обычное/овсяное/безлактозное/без молока) | отдельный товар Эвотор («Молоко овсяное») | Inventory |
| Сиропы (лаванда/карамель/ваниль) | товар-топпинг, `groupKey = "syrup"` | Inventory |
| Сахар (0/50/100%) | товар-топпинг, `groupKey = "sugar"` | Inventory |
| Добавки (двойной шот, корица) | товар-топпинг, `groupKey = "extra"` | Inventory |

Следствия:
- Ни одной дельты цены на клиенте — цена любой опции приходит из Inventory.
- Все опции с `evotorUuid` идут отдельными строками чека → склад и отчётность корректны.
- Опция без `evotorUuid` показывается, но помечается «нет в кассе» и не даёт добавить позицию.
- Требуется доработка каталога/админки: завести товары размеров и молока, проставить `groupKey`.
- `data/Pricing.kt` при этом остаётся нужен — для `modsLine()` (подпись состава) и
  суммы уже посчитанных цен; но он **не считает дельты**, а складывает цены товаров.

Остальные варианты (B — дельты на клиенте, C — гибрид) отклонены: ломают склад и состав чека.

**Вариант B.** Дельты считаются на клиенте, в чек уходит одна позиция с итоговой ценой.
Быстро, но: нет списания склада модификаторов, в чеке нет состава, отчётность врёт.

**Вариант C.** Гибрид: размер/молоко — отдельные товары (влияют на чек), сироп/сахар —
клиентские дельты (в чек идут как топпинги, если есть uuid, иначе в цену).
Компромисс, но сложнее в поддержке.

> Без ответа на этот вопрос делать экран 07 и ценообразование нельзя.

## 8. Фискальный слой (что и как через Эвотор)

| Операция | API |
|---|---|
| Продажа | `OpenSellReceiptCommand` + `NavigationApi.createIntentForSellReceiptPayment()` — **уже есть** |
| Скидка (подарок, кэшбэк, комбо) | `SetExtra("sc", …)` + `DiscountIntegrationService` — **уже есть**, расширить на комбо |
| Внесение наличных | `PayInCommand` |
| Изъятие / инкассация | `PayOutCommand` |
| X-отчёт | X-report API (без закрытия смены) |
| Закрытие смены | Z-report API |
| Остаток в кассе | Только из ответа отчёта, не из локального счётчика |

Правило: **APK никогда не показывает как факт то, что не подтверждено Эвотором или сервером.**
Если операция не прошла — экран говорит «не проведено», а не «готово».

## 10. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| `MainActivity.kt` разрастётся до 5–6 тыс. строк и станет нередактируемым | Высокая | Вынести новые sheet-ы в отдельные файлы (§5.1), не добавлять в `MainActivity` |
| Комбо-скидка разойдётся между превью и чеком | Высокая | Одна функция `DiscountCalc.compute()` для всех трёх мест + юнит-тест на равенство |
| Миграция JSON корзины сломает восстановление после падения | Средняя | Версия схемы в `Cart.save()`, чтение старых ключей с дефолтами |
| Демо-данные `index` попадут в прод | **Критическая** | Правило: ни одного ФИО/суммы/даты из прототипа в коде APK |
| `targetSdk 30` / ST5: тени, `elevation`, шрифт Onest | Средняя | Проверка на реальном ST5, Onest в `res/font` (сейчас системный) |
| Бэкенд не успеет | Средняя | Этапы 9–12 за фича-флагом: экран честно говорит «нет данных» |
