# 6.7 Coffee — кассовый клиент Эвотор (5.1.0-addons-contract / versionCode 115)

## Поток
1. Карта: QR (токен резолвится на backend) или короткий номер; можно продолжить без карты.
2. Заказ: каталог терминала (`InventoryApi` / ProductTable) + схемы добавок с backend, поиск, плитки;
   липкая нижняя панель с суммой чека и «В чек»; корзина — шторка. Каталог обновляется
   pull-to-refresh, из меню «Ещё» и автоматически при возврате в приложение (не чаще раза в 60 с).
3. «В чек»: если у карты есть живой резерв — компактный лист «Лояльность» (подарок / списание
   кэшбэка). **Экрана оплаты в APK нет**: способ оплаты, сумма, сдача и чек — это Эвотор POS.
4. Перед отправкой корзина сверяется с последним каталогом (`ReceiptValidator`): удалённый товар,
   исчезнувшая/недоступная добавка или платная добавка без `evotorUuid` в чек не отправляются.
5. Позиции уходят одним `OpenSellReceiptCommand(positionAddList, setExtra)`; по OK сразу
   `NavigationApi.createIntentForSellReceiptPayment()` — управление возвращается Эвотору.
   Товар — одна позиция, каждая платная добавка — отдельная позиция со своим `evotorUuid`.
6. `extras` чека: `{ "<APP_UUID>": { "sc": {v:2,c,op,free,cb,ts,kind} } }` + плоский `sc`;
   скидку и extras пишет `DiscountIntegrationService`. Чашки начисляет сервер по фискальному документу.
7. Backend обрабатывает SELL по poll и начисляет бонусы. Loyalty-запросы идут через HTTPS-прокси Эвотора
   (секретов в APK нет).

Подробности и список изменений: `CHANGELOG-5.1.0-addons-contract.md` (добавки) и `CHANGELOG-5.0.0-evotor-receipt.md` (передача позиций в POS).

## Сборка
`./gradlew :app:assembleRelease -PAPI_BASE_URL=https://app.67coffee.ru`
Без `KEYSTORE_FILE`/`KEYSTORE_PASSWORD`/`KEY_ALIAS`/`KEY_PASSWORD` release подписывается debug-ключом
(так APK ставится на терминал); с этими параметрами — вашим release-ключом.
Единицы цены: `-PPRICE_UNITS=KOPECKS|AUTO|RUBLES` (по умолчанию KOPECKS — так делает integration-library). Правило подарка — `FreeCupRules` (см. CHANGELOG-CASHIER-UX-v2.md).
Тесты: `./gradlew :app:testDebugUnitTest`.

## Очередь бариста

`PENDING` (чек открыт, номера нет) → `CONFIRMED` (оплата подтверждена, номер присвоен) → `READY`.
Отмена в POS удаляет `PENDING` без расхода номера; TTL 10 минут переводит забытый `PENDING`
в `EXPIRED`. Бариста по умолчанию видит только `CONFIRMED`; флаг `queueShowPending`
(`OrderQueueStore.setShowPending`) включает показ ожидающих для точек, где готовят заранее.
Итоги смены (`tally`) учитывают только `CONFIRMED`/`READY`.

## Трактовка `maxCount` (зафиксировано)

Контракт каталога описывает `maxCount` как предел количества одной опции. В кассе принято
решение (**вариант «б»**): `maxCount` — это предел числа **разных** опций в группе,
две порции одной добавки не продаются, повторный тап по выбранной опции ничего не добавляет.

- В коде поле читает `ToppingRules.groupLimit(...)` — имя выбрано специально, чтобы
  расхождение с формулировкой контракта не искали как баг.
- Поведение закреплено тестом `groupLimit caps distinct options in a group - documented maxCount interpretation`.
- Если бизнесу понадобится количество у одной опции (сироп ×2 отдельной строкой чека),
  это отдельная задача: меняется состав чека и `CartLine`.
