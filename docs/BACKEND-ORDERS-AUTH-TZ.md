# ТЗ для backend (`sixth-cup`): авторизация `/api/devices/orders/*` для кассы

Дата: 2026-11-08. Заказчик: APK `evotor-app` 163–165. Проблема: касса получает
`401 Unauthorized` на всех маршрутах предзаказов, лояльность и каталог при этом работают.

## 1. Симптом

```
GET /api/devices/orders/active 401 1ms error="Unauthorized"   (каждые 10 с — опрос баннера)
```

На экране кассы: «Терминал не авторизован. Перепривяжите кассу».
При этом `POST /api/devices/loyalty/resolve` (привязка карты) и `GET /api/devices/catalog`
выполняются успешно, терминал виден в админке.

`GET https://app.67coffee.ru/api/devices/orders/active` без прокси-токена Эвотора снаружи даёт
`403 proxy_forbidden` (Caddy), т.е. с кассы запрос **проходит** прокси и доходит до Node —
и уже там получает `401`.

## 2. Причина

Маршруты `/api/devices/orders/*` защищены проверкой device-токена (`X-Device-Token` из enroll).
APK этот заголовок **никогда не отправлял**: в приложении нет ни enroll, ни хранения токена
(см. `docs/BARISTA-FLOW-V2.md` — используется только прокси-токен Эвотора).
`/loyalty/resolve` и `/catalog` такой проверки не требуют, поэтому работают.

Итог: админская привязка устройства не даёт APK никакого секрета; отправить в `X-Device-Token`
нечего. Нужно либо ослабить авторизацию orders до уровня остальных device-маршрутов (вариант A),
либо реализовывать enroll в APK (вариант B, требует отдельного контракта).

## 3. Что именно отправляет APK (по факту)

Все запросы `GET/POST/PATCH` на `/api/devices/orders/*`:

| Заголовок | Значение | Примечание |
|---|---|---|
| `Authorization` | секрет прокси Эвотор | ставит облако Эвотора, в APK его нет |
| `X-Evotor-Store-Uuid` | UUID точки из `StoreUuidResolver.peek()` | может отсутствовать, если точка ещё не определена |
| `X-Evotor-Device-UUID` и `X-Evotor-Device-UUID` (оба регистра) | `Settings.Secure.ANDROID_ID` терминала | стабилен для кассы |
| `X-App-Version-Code` | `165` | |
| `X-App-Version-Name` | `5.3.6-audit-p1` | |
| `Content-Type` | `application/json` | |
| `X-Device-Token` | **не отправляется** | причина 401 |

`PATCH` отправляется как `POST` + `X-HTTP-Method-Override: PATCH` (и повторная попытка реальным PATCH).

Эндпоинты: `GET /active`, `GET /resolve`, `PATCH /:id/status`, `POST /:id/reject`,
`POST /:id/mark-paid` (в будущем `POST /:id/eta`).

## 4. Требуемое изменение (вариант A — предпочтительный)

**Авторизовать `/api/devices/orders/*` так же, как `/api/devices/loyalty/resolve` и `/api/devices/catalog`:**
прокси-авторизация + `X-Evotor-Store-Uuid`; `X-Device-Token` сделать **необязательным**.

Псевдокод middleware:

```ts
// orders router
const storeUuid = req.get('X-Evotor-Store-Uuid')?.trim();
if (!storeUuid) return res.status(400).json({ ok: false, error: 'bad_request', message: 'no store uuid' });
const store = await stores.findByUuid(storeUuid);        // тот же резолвер, что у catalog/loyalty
if (!store) return res.status(403).json({ ok: false, error: 'wrong_store' });

// опционально: если X-Device-Token передан — валидировать как раньше;
// если не передан — не требовать (доверяем прокси-авторизации кабинета).
```

Правила:

1. **Не возвращать 401 из-за отсутствия `X-Device-Token`.**
2. Если `X-Device-Token` передан и невалиден/просрочен — можно вернуть `401 unauthorized`
   (строгий режим для будущих сборок), но отсутствие заголовка ошибкой не считать.
3. Магазин брать из `X-Evotor-Store-Uuid` (как catalog) и **всегда** сверять с `order.storeId`:
   чужой заказ → `403 wrong_store` (уже есть).
4. `X-Evotor-Device-UUID` — только для логов/диагностики (или как дополнительный ключ поиска
   устройства в админке), но не как единственный фактор авторизации.
5. Если store UUID не пришёл — `400 bad_request` (не 401), чтобы APK показал понятную ошибку
   и не выглядело как «перепривяжите кассу».

### Почему это безопасно

- Прокси-токен выдаётся кабинетом Эвотор и не лежит в APK; запрос без него отсекает Caddy (`403 proxy_forbidden`).
- Каталог и лояльность уже работают по этой модели — orders не даёт доступа к деньгам/начислениям,
  только чтение и смена статуса предзаказа в рамках своей точки.
- Скоуп точки сохраняется жёстко (`order.storeId == store.id`), как и сейчас (`403 wrong_store`).

### Остаточный риск (осознанно принимаем)

Терминал точки технически может подставить чужой `X-Evotor-Store-Uuid`, если знает его.
Этот риск уже существует для catalog/loyalty. Если нужен более строгий режим — привязать
`X-Evotor-Device-UUID` к точке в админке (device registry) и требовать совпадения пары
`store + device`. В таком случае APK ничего менять не надо: он уже шлёт оба заголовка.

## 5. Вариант B (если 401 должен остаться)

Тогда нужен контракт enroll для APK, минимум:

1. `POST /api/devices/enroll` (или админский код): вход — код из админки + `X-Evotor-Device-UUID`,
   выход — `{ deviceToken, storeUuid, expiresAt }`.
2. Имя заголовка и формат токена (`X-Device-Token`), TTL и порядок ротации.
3. Как кассир вводит код на терминале (экран в APK) и что делать при истечении.
4. Требования к хранению (SharedPreferences) и отзыву токена.

Без этого пункта APK-часть реализована быть не может — сейчас в приложении нет ни экрана,
ни хранилища токена.

## 6. Критерии приёмки (вариант A)

| # | Проверка | Ожидание |
|---|---|---|
| 1 | `GET /api/devices/orders/active` с заголовками APK (без `X-Device-Token`) | `200 {ok:true, orders:[...]}` |
| 2 | Он же без `X-Evotor-Store-Uuid` | `400 bad_request` (не 401) |
| 3 | `GET /resolve?code=…` для заказа другой точки | `403 wrong_store` |
| 4 | `PATCH /:id/status` без токена устройства | работает по статусам, некорректный переход → `409 invalid_transition` |
| 5 | `POST /:id/mark-paid` без токена устройства | идемпотентно `200` |
| 6 | `X-Device-Token` передан и невалиден (если включён строгий режим) | `401 unauthorized` |
| 7 | Лояльность/каталог | без изменений |
| 8 | Контракт `extras.sc` (`preorder`, `ord`, `qn`, `free`, `cb`) | без изменений |

## 7. Тесты backend (vitest)

- `orders/auth.spec.ts`:
  - без `X-Device-Token`, с валидным store → `200`;
  - без store UUID → `400`;
  - неизвестный store → `403`;
  - заказ чужой точки → `403 wrong_store`;
  - `X-Device-Token: garbage` → поведение по выбранному режиму (401 либо игнор — зафиксировать в тесте);
  - `mark-paid` дважды → оба `200`, резерв не задваивается.
- регресс: `loyalty/resolve`, `catalog` — прежние ответы.

## 8. Выкладка и проверка на кассе

1. Задеплоить backend (APK обновлять не нужно).
2. На терминале открыть «Заказы»: баннер/очередь появляются ≤ 10 с, без 401 в логе.
3. Проверить: принять заказ → у гостя «Принят»; «Готовится»/«Готов»; «В чек» → SELL → `mark-paid`;
   заказ другой точки → 403, ничего не добавлено.
4. В логе APK не должно быть `OrderApi ... status=401`.
