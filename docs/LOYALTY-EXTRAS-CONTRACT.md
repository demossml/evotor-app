# Контракт `extras.sc` для лояльности (APK ↔ backend)

Что касса кладёт в фискальный чек, чтобы backend после `SELL` провёл начисление и списание.
Спецификация backend — `sixth-cup`: `backend/src/integrations/evotor/loyaltyExtras.ts`,
`processing/SellHandler.ts`. Этот файл описывает **сторону APK**.

## Кто что проверяет

| Проверка | Где выполняется |
|---|---|
| Подпись QR-токена гостя (Ed25519), срок действия, `key id` | **только backend** (`SellHandler` → `verifyServerToken`) |
| Существование карты, блокировка, состояние резерва | backend (`resolve`, `SellHandler`) |
| Что из бонусов реально доступно и сколько списать | backend (`resolveAndReserve`, клэмпы в `SellHandler`) |

**APK не проверяет криптографию.** В сборке нет ни публичного ключа, ни кода проверки подписи:
токен уходит в чек как есть, решение принимает сервер. Прежняя формулировка контракта
(«the APK verifies the Ed25519 signature…») описывала намерение, а не реализацию.

## Форма

```json
{
  "<BuildConfig.APP_UUID>": { "sc": { "v": 2, "c": "…", "ts": 1730000000000, "kind": "token", "op": "R-…", "free": 1, "cb": 500 } },
  "sc": { "v": 2, "c": "…", "ts": 1730000000000, "kind": "token", "op": "R-…", "free": 1, "cb": 500 }
}
```

Оба ключа содержат **идентичный** объект: backend читает плоский `sc` первым, затем
`extras[EVOTOR_APP_ID].sc`, затем любой объект с полем `sc`. Документ один, поэтому
дублирование ключа не приводит к двойному начислению.

## Поля

| Поле | Обяз. | Значение |
|---|---|---|
| `v` | да | версия схемы, `2`. Backend игнорирует `sc` с `v < 2` |
| `c` | да | **QR:** подписанный серверный токен. **Ручной ввод:** канонический цифровой код карты (`cardCode` из ответа `resolve`, без пробелов и ведущих нулей) |
| `ts` | да | unix-время в миллисекундах (метка формирования extras) |
| `kind` | да | `token` / `code` — метка для журнала. Backend её **не читает** и решает по форме `c` |
| `op` | только при резерве | `reservationId` из `resolve`. Без него backend не потребляет резерв, и `free`/`cb` игнорируются |
| `free` | да | `1`, если бариста выбрал подарок **и** есть живой резерв, иначе `0` |
| `cb` | да | сумма кэшбэка к списанию в **копейках**, `0` без резерва |
| `q` | нет | sequence карты, только если сервер его прислал (`CardInfo.seq > 0`). Сейчас backend его не отдаёт; отсутствие `q` чек не блокирует и на начисление не влияет |
| `ord` | нет | `orderId` из `POST /api/devices/queue-number` — канонический ключ связи чека с `queue_numbers` |
| `qn` | нет | публичный номер заказа строкой. Только для логов: источник истины — `ord` |
| `voucherId` | только QR + резерв | id экземпляра ваучера из `resolve.vouchers[]`. По числовому коду карты ключа **нет никогда** |

## Ваучер и кэшбэк: одна денежная скидка на чек

Backend **не** запрещает прислать `cb` и `voucherId` одновременно — спишет оба. Поэтому
инвариант живёт в кассе:

1. ваучер выбран → `cb = 0`, кэшбэк остаётся на балансе гостя;
2. кэшбэк выбран → `voucherId` в `sc` не пишется, ваучер не гасится;
3. оба состояния физически невозможны: `Choice.normalize()` в
   [data/Choice.kt](../app/src/main/java/ru/sixthcup/evotor/data/Choice.kt) обнуляет второе поле.

Скидку в рублях считает только касса, backend её не пересчитывает и с ОФД не сверяет:

- `percent` — процент **от остатка после подарка**, вниз до копеек;
- `fixed` — сумма в **копейках** (backend хранит её так: `30000` = 300 ₽), не больше остатка;
- ваучер с `stackableWithFreeCup = false` не применяется вместе с подарком (UI + расчёт);
- `total` в `ReceiptDiscountEventResult` — это **сумма скидки** (подарок + ваучер + кэшбэк),
  а не сумма к оплате.

## Почему `c` — это токен, а не номер карты

Backend выбирает ветку обработки по форме значения:

- `c` содержит `.` → подписанный токен → `verifyServerToken`, возможен `consumeReservation(sc.op)`;
- `c` — только цифры → «ручной код»: карта найдена по `card_code`, чашки начисляются,
  но **списание подарка и кэшбэка = 0**.

Поэтому отправка номера карты вместо токена (регрессия версии 5.0.0, коммит `57a5c5f`)
приводила к тому, что касса давала скидку по резерву, а `cards.free_used` и
`users.cashback_balance` не уменьшались. Исправлено: `CardSession.scValue()`.

Ручной ввод кода остаётся «начисление без списания» — это осознанное правило
(номера карт подбираемы), а не дефект.

## Офлайн

Сервер недоступен: подписанный QR всё равно попадает в чек (backend проверит подпись и
начислит чашки), но `op`/`free`/`cb` не выставляются. Числовой код офлайн не принимается.
