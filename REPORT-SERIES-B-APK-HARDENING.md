# Отчёт Series B — hardening APK (5.3.17, versionCode 176)

Дата: 2026-11-18  
База: `a8676b8` (5.3.16-switch-client)  
Сборка: `app/build/outputs/apk/release/app-release.apk`

## 1. Авторизация / device-контур

**Что закрыто в APK**

- Все device-запросы, которым нужна точка, теперь **не уходят без UUID точки**:
  orders, loyalty/resolve, customers lookup/register, queue-number, shift.
  Вместо запроса возвращается понятная ошибка `missing_store`.
- `401/403` больше не маскируются под «нет связи»: кассир видит, что терминал не авторизован.
- Убрано «полуоткрытое» поведение карты: при **любом HTTP-отказе** (400/401/403/404/409/429/5xx)
  карта не прикрепляется к чеку. Подписанный QR остаётся только при сетевом исключении/таймауте,
  без бонусов, чтобы чашка могла быть начислена после продажи.
- `DeviceHeaders` по-прежнему не содержит секретов: `Authorization` добавляет Evotor Cloud.
  `X-Device-Token` не отправляется, потому что в APK нет контура enroll и самого токена.

**Что осталось на стороне backend**

- `deviceStoreAuth` всё ещё принимает один `X-Evotor-Store-Uuid`; это не является
  криптографической аутентификацией. Нужен вариант A из `docs/BACKEND-ORDERS-AUTH-TZ.md`
  (прокси-авторизация + store + сверка `order.storeId`) либо полноценный enroll с device token.
- Если `EVOTOR_PROXY_TOKEN` не задан, серверная проверка прокси сейчас имеет fail-open.
  APK это исправить не может.

## 2. Заказы, статусы, оплата, идемпотентность

- `mark-paid` защищён от параллельного дублирования: один заказ — один активный поток.
- `409 already_paid` считается успехом по смыслу: локальный pending снимается, заказ обновляется,
  повторный SELL не инициируется.
- `409 invalid_transition` не повторяется, но список активных заказов перечитывается.
- `409 benefit_conflict` показывает кассиру понятное сообщение и не ретраится.
- Сетевые ошибки, `5xx`, `408`, `429` повторяются ограниченно (до 3 попыток); `4xx` — нет.
- Общий текст `http_409` и `http_429` добавлен в `PreorderQueue.errorText`.
- Клиентская защита от двойного нажатия «В чек» (`sendingReceipt`) сохранена.

**Остаточный риск**

- Атомарность оплаты и уникальность SELL окончательно обеспечиваются backend/POS.
  APK снижает вероятность дублей, но не заменяет серверную идемпотентность.
- Реальный сценарий с двумя кассами/реконнектом нужно проверить на терминале.

## 3. Лояльность и списание

- Числовой код карты (`identifiedBy=CODE`) **не даёт списания** free/cashback даже при ошибочно
  присланном `reservationId`/`canRedeem`.
- Безопасный proof: подписанный QR-токен или телефонная бонусная карта, подтверждённая сервером.
- `free`/`voucher` требуют QR + живой резерв; `cashback` по QR требует резерв, по телефону —
  серверный `canRedeem`.
- Добавлены понятные сообщения для `429` (лимит запросов) и `409 reservation_conflict`
  (карта занята другим чеком).
- Прогресс/подарок по ручному коду можно показать, но списание по нему заблокировано.

**Остаточный риск**

- Телефонный lookup — не криптографический proof. Если backend разрешает `canRedeem` по телефону,
  окончательная защита остаётся серверной.
- Ручной номер карты всё ещё используется для идентификации/начисления по политике backend;
  для списания он закрыт на стороне APK.

## 4. Финальная проверка

- `./gradlew testDebugUnitTest` — **656 тестов, 0 падений**.
- `./gradlew assembleRelease` — успешно, `lintVitalRelease` пройден.
- APK: `ru.sixthcup.evotor`, `versionCode=176`, `versionName=5.3.17-series-b-hardening`,
  minSdk 23, targetSdk 30.
- Код SELL/PAYBACK/печати и построение чека не переписывались; изменения касаются
  preconditions, обработки ошибок и проверки proof.
- На реальном терминале вручную не проверялось: нужен прогон QR заказа → SELL → mark-paid,
  PAYBACK, печать и повторный скан.

**Итоговая оценка готовности:** контур стал заметно безопаснее на стороне APK, но
полная защита device-API зависит от backend (fail-open прокси и доверие к storeUuid).
