# 6.7 Coffee · Evotor — 5.0.0-evotor-receipt (versionCode 114)

Касса перестала быть «оплатой»: APK собирает позиции и отдаёт их Эвотору. Оплату, суммы,
сдачу и фискальный чек делает только Evotor POS.

## Что удалено

| Удалено | Где было |
|---|---|
| Экран/лист оплаты: «К ОПЛАТЕ», способы «Картой / Наличными», кнопки оплаты | `MainActivity.checkout()` |
| Калькулятор наличных: «Получено», «Сдача», быстрые суммы, клавиатура | `MainActivity.showCashSheet()`, поле `payDue`, хелпер `bottomBorder()` |
| Метод `pay()` (двойной тап → оплата) | заменён на `sendReceipt()` |
| Экран `Screen.PAYMENT` + `renderPayment()` | `MainActivity` |
| Экран `Screen.DONE` + `renderDone()` («Оплачено», «Чек пробит») | `MainActivity` |
| `renderDone`-снимки `doneLines/doneTotal/doneCard/doneOrder` | `MainActivity` |

Новых экранов оплаты нет. Вместо них: лист «Лояльность» (только подарок/кэшбэк из резерва)
и сразу передача позиций в Эвотор.

## Новый поток продажи

```
Витрина → карточка товара (объём, молоко/сироп/сахар/добавки) → «В чек»
        → [лист «Лояльность», если есть живой резерв и льгота]
        → ReceiptValidator: сверка корзины с последним каталогом
        → OpenSellReceiptCommand(positionAddList, setExtra)
        → NavigationApi.createIntentForSellReceiptPayment()  ← управление у Эвотора
        → POS: оплата, сдача, фискальный чек
```

Кнопки: нижняя панель и футер корзины — «В чек» (было «К оплате»), CTA листа рекомендаций —
«В чек · сумма». Сумма в панели — сумма позиций чека, не «сумма к оплате».

## Очередь бариста: состояния вместо фантомных заказов

Номер выдавался при открытии чека, поэтому отменённая в POS оплата оставляла заказ в очереди
навсегда. Теперь у записи есть состояния:

```
PENDING ──(чек закрыт, оплата прошла)──► CONFIRMED ──► READY
   │                                         ▲
   ├──(чек остался открытым)──► удаление     └──(«В работу» из READY)
   └──(TTL 10 мин)────────────► EXPIRED
```

* PENDING создаётся при открытии чека: состав фиксируется, **номер не тратится**, бариста не видит;
* CONFIRMED — по тому же сигналу, что чистит корзину в `onResume` (SELL-чек закрыт): тогда же
  присваивается номер и делается запись в tally смены;
* чек остался открытым → PENDING удаляется, номер не израсходован (нумерация без дыр);
* приложение убили до возврата из POS → через 10 минут запись становится EXPIRED и вычищается;
* по умолчанию бариста видит только CONFIRMED; `OrderQueueStore.setShowPending(true)` —
  для точек, где начинают готовить до оплаты;
* `tally` смены считает только CONFIRMED/READY.

Кнопка «✕» в строке очереди удаляет заказ: у PENDING — по `id`, у подтверждённых — по номеру.

## Состав чека

* позиция 1 — товар: `evotorUuid` выбранного SKU/размера, цена терминала;
* позиции 2..N — каждая **платная** добавка отдельной позицией со своим `evotorUuid`;
* не попадают: `zeroOption`, `available=false`, добавки без `evotorUuid`, папки-группы, `mod:`-синтетика;
* если цена каталога разошлась с номенклатурой терминала — в чек уходит цена терминала,
  расхождение пишется в лог (`price_mismatch`), APK ничего не «исправляет».

## Добавки (правила соблюдены в коде)

`data/ToppingRules.kt` — единственный источник правил, его используют UI и проверка чека:

* `milk`/`syrup`/`sugar` — одиночный выбор, `extra` — до `maxCount` группы;
* `isDefault` — предвыбран; платную опцию сами не отмечаем (иначе в чек попадёт сумма,
  которую гость не выбирал);
* `required` — без выбора позиция не уходит в чек (CTA заблокирована и объясняет причину);
  `zeroOption` и `isDefault` закрывают требование автоматически, платную опцию выбирает кассир;
* `zeroOption` не создаёт позицию в чеке и не меняет сумму;
* `available=false` — заблокировано («нет в кассе»);
* платная добавка без `evotorUuid` — заблокирована в UI и отклоняется валидатором;
* повторный выбор одной опции невозможен (ключ `t:<id>` + `cartKey` корзины).

`data/ReceiptValidator.kt` перед «В чек» сверяет строки корзины с последним каталогом:
`product_not_found` (товар удалён), `option_removed`, `option_unavailable`,
`option_without_uuid`, `option_changed`. При проблеме чек не открывается: диалог со списком,
«Убрать и обновить» удаляет невалидные строки и перезагружает каталог.

## Лояльность и extras

`extras` чека:

```json
{
  "151071e8-88a4-44f6-b71a-b17c559f9b7d": {
    "sc": { "v": 2, "c": "0001234", "op": "<reservationId>", "free": 1, "cb": 700, "ts": 1761331200000, "kind": "code" }
  },
  "sc": { "v": 2, "c": "0001234", "op": "<reservationId>", "free": 1, "cb": 700, "ts": 1761331200000, "kind": "code" }
}
```

* `c` — `cardCode` из ответа `resolve` (фолбэк — отсканированное значение для офлайн-QR);
* `ts` — unix **ms** (было секунды), `kind` — `token` | `code`;
* `op` пишется только при наличии резерва; `cb` — копейки;
* вложенный ключ `appId` — новый формат, плоский `sc` оставлен для текущего парсера;
  значения идентичны, документ один — двойного списания нет.

`POST /api/devices/sales` из кассы не вызывается.

## Каталог и кэш

* `GET /api/devices/catalog?storeUuid=…` + `X-Evotor-Store-Uuid` на каждый запрос;
* таймауты connect 5 с / read 10 с; на 5xx и сетевые ошибки — 1 с, 3 с, максимум 3 попытки;
* фоновое обновление при возврате в приложение — не чаще 1 раза в 60 с; ручное —
  pull-to-refresh и меню «Ещё → Обновить каталог»;
* кэш хранит время сохранения; при ошибке сети/5xx/пустом `products: []` кэш не затирается,
  в шапке плашка «… — данные от HH:MM»;
* `CatalogCache` сохраняет `groupId/variantLabel/variantSort/sizeValue/sizeUnit` и
  восстанавливает производные карты (`byNameExact`, `byGroupId`, `nameGroupId`).

## Логи кассы

`net/DeviceLog.kt` → `POST /api/devices/logs`, пачки ≤ 20 записей, тело ≤ 16 КБ,
≤ 120 запросов/мин, сообщение ≤ 500 символов, fire-and-forget (ошибка лога продажу не блокирует).
Пишем: старт сессии, каталог (кол-во товаров/добавок, недоступность), `loyalty_resolve_ok/fail`,
применение скидки, `price_mismatch`, отказ по добавке без UUID, состав чека, открытие/отказ чека.
QR/token/Authorization не отправляются (`DeviceLog.redact`).
